# Архітектура (чернетка)

> Загальна картина того, як компоненти системи будуть зв'язані.
> Деталі кожного блоку — в окремих документах (`04-database.md`,
> `05-api.md`, `06-admin.md` і т.д.). Частина рішень тут ще TBD.

## Загальна схема

Flask-застосунок (Python), server-side rendering через Jinja2-шаблони.
Окремий (захищений) блок адмінки — CRUD для тренерів, прайсу,
розкладу, школи інструктора.

```
Браузер користувача
      │
      ▼
Flask-застосунок (app.py, routes)
      │
      ├── Jinja2-шаблони (templates/) — HTML сторінок
      ├── Власна БД — тренери, прайс (+ таблиця відповідності назв),
      │                розклад (?), школа інструктора
      ├── Адмінка (CRUD) — окремий захищений розділ для власника
      └── Зовнішні інтеграції:
            ├── Букінг/CRM API — зараз віддає дані розкладу та
            │     прайсу (джерело поки зовнішнє, документуємо в
            │     05-api.md)
            ├── Платіжна система — кнопка "Оплатити" на прайсі
            ├── Fit Control (мобільний застосунок) — сторонній,
            │     тільки посилання (Google Play / App Store)
            └── Месенджери (Viber/Telegram/Instagram) — вхідні
                  вебхуки в адмінку (єдиний інбокс, розділ 06-admin.md)
                  + кнопки запису на масаж/сауну/реабілітацію на сайті
```

## Ключові підсистеми

1. **Каталог тренерів** — єдина БД-сутність, використовується на
   трьох сторінках: Команда (усі, з фільтрами за напрямком і
   кваліфікацією), Масаж (підмножина "масажисти"), Реабілітація
   (підмножина "реабілітологи"). Кожен тренер має категорію/напрямок,
   кваліфікацію, опис; для реабілітологів — ще й власну ціну занять,
   привʼязану саме до конкретного тренера (а не до єдиного прайс-листа).

2. **Прайс** — двоступеневий фільтр: категорія → залежний другий
   фільтр (термін / стать-вік / кваліфікація / відсутній, залежно від
   категорії). На старому сайті ще не добудований до кінця; дані йдуть
   з **того самого API, що й розклад** (не окреме API — усі потрібні
   поля вже там). Додатково є три власні таблиці власника в Wix, які
   потрібно перенести в нашу БД:
   1. Таблиця фільтрів/назв для категорій "Масаж" і "Персональні"
   2. Таблиця тексту нижньої інформаційної плашки (умови абонемента)
   3. Таблиця відображуваних назв абонементів (щоб адмін міг сам
      редагувати назви без втручання розробника)

3. **Розклад** — тижневий календар тренувань з фільтрами за тренером
   і видом тренування, зараз повністю з API в реальному часі (разом
   із позначкою "Актуально на..."). Після переписування логіка
   відображення лишається такою ж — споживаємо той самий чи новий API.

4. **Школа інструктора** — великий окремий блок: адмінка для
   лекцій/відео, доступ студентів за email, таблиця випускників.
   Деталі — `docs/pages/10-school-instructor/`.

5. **Єдиний інбокс повідомлень (нова підсистема, додана пізніше).**
   Окремий розділ адмінки — агрегатор вхідних повідомлень з Telegram,
   Viber та Instagram в одній стрічці, з відповіддю клієнту напряму з
   адмінки. Без прив'язки до внутрішньої бази клієнтів — це просто
   "вікно" в чужі месенджери, не CRM. Технічно — вхідні вебхуки від
   кожної платформи (Telegram Bot API, Viber Bot API, Instagram Graph
   API) на окремі ендпоінти нашого застосунку + власні таблиці
   діалогів/повідомлень. Це **свідомо додана вимога** — раніше
   планувалось, що месенджери лишаються "як є" (див. лог рішень у
   `01-project.md`). Деталі ролей і екранів — `06-admin.md`.

## Рішення, які вже прийняті (доповнення)

- **СУБД визначено — PostgreSQL** (на сервері розробника застосунку).
  ORM / інструмент міграцій схеми (наприклад SQLAlchemy + Alembic) —
  ще TBD
- **Окремий публічний, версійований REST-API (на кшталт `/api/v1/...`)
  не потрібен.** Усі клієнти/мобільний досвід закриті всередині
  застосунку Fit Control, власного мобільного застосунку не
  планується — отже, фронтенд переважно рендерить дані напряму в
  Jinja2-шаблонах через Flask, без додаткового API-шару між БД і
  фронтендом.
  > Уточнення: це **не** забороняє невеликі внутрішні AJAX-ендпоінти
  > для конкретних інтерактивних шматків сторінки — наприклад,
  > підвантаження карток тарифів при перемиканні фільтра на Прайсі
  > без перезавантаження сторінки. Такі ендпоінти живуть у
  > blueprint'і відповідної сторінки (наприклад `/price/cards`, а не
  > `/api/v1/price`), повертають дані лише для власного фронтенду і
  > не є публічним API для зовнішніх споживачів. Так само вебхуки
  > месенджер-ботів єдиного інбоксу (`/admin/inbox/webhook/...`,
  > підсистема 5 вище) — це вхідні інтеграційні ендпоінти, а не
  > REST-API в цьому сенсі.
  > Колбек від LiqPay при оплаті — **не наш ендпоінт**: банк шле його
  > на сервер розробника застосунку (`05-api.md`, розділ 6.5), від
  > нашого Flask тут нічого не залежить
- **Оплата:** запити до платіжної системи надає розробник застосунку,
  сидить на тому ж сервері — деталі інтеграції очікуються
