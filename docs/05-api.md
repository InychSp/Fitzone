# Зовнішнє API: servpost.php

> Довідник побудований на основі двох джерел: (1) PDF від розробника
> застосунку ("Fitzone / F3 — справочник по servpost.php") і (2)
> **фінальний робочий код** сторінки Прайс на Wix — два бекенд-модулі
> (`payment.web.js`, `pricing.web.js`), три HTML-віджети сторінки і
> код самої сторінки (Velo page code). Це єдине зовнішнє джерело даних
> для розкладу та прайсу — окремого API для прайсу немає.
>
> Там, де робочий код підтверджує або уточнює PDF — довіряємо коду,
> це позначено окремо в кожному розділі.

## Загальна інформація

| Параметр | Значення |
|---|---|
| Сервер | `https://app.fitzone.com.ua` |
| Шлях скрипта | `/zdeccidatmoiscripti/servpost.php` |
| Метод | POST |
| Формат відповіді | чистий JSON (порожній JSON, якщо даних немає) |

> На тому самому сервері є ще два скрипти, які використовуються лише
> для оплати (розділ 6): **`genmanid.php`** (резервування ID) і
> **`liqpay_checkout.php`** (сам редирект на оплату). Все інше —
> розклад, прайс — тільки через `servpost.php`.

## Параметри запиту

- **A** — масив, визначає клуб: `[1,1]` — FitZone, `[1,2]` — Ф3
- **B** — рядок із SQL-запитом; конкретний запит відрізняється для
  кожної задачі (див. розділи нижче)

> ⚠️ **Технічна примітка.** Параметр `B` приймає "сирий" SQL-текст.
> У нашому Flask-бекенді маємо використовувати лише фіксовані,
> заздалегідь підготовлені запити (як задокументовано нижче) і
> ніколи не підставляти туди довільний користувацький ввід — щоб не
> відкрити SQL-injection через проксі-виклик цього API.

> **Підтверджено робочим кодом:** реальні ключі JSON-тіла запиту —
> **малими** літерами, не великими, як у PDF:
> ```json
> { "a": [1,1], "b": "SELECT ..." }
> ```
> `genmanid.php` (розділ 6.3) приймає так само `a`/`b`/`c`/`d` малими
> літерами. Позначення `A`/`B`/`C`/`D` в PDF, найімовірніше, описує
> параметри "по суті", а не буквальні ключі. Орієнтуємось на реальний
> код скрізь нижче.

## Про клуби (мультитенантність)

Цей API обслуговує одразу два клуби на одному сервері: **FitZone**
(`idz=1`) і **Ф3** (`idz=2`). У всіх SQL-запитах `idz` у тілі запиту
має відповідати параметру `A`. **Для нашого сайту цікавий лише
`idz=1` (FitZone).**

## Boolean-поля

Значення можуть приходити в різному вигляді:
- false ⇔ `Null`, `f`, `false`, `0`
- true ⇔ `t`, `true`, `1`

Формат непостійний — на боці Flask потрібна власна нормалізуюча
функція при парсингу відповіді.

## ⚠️ Нормалізація відповіді: іноді повертається "голий" об'єкт

За описом розробника: коли SQL-запит повертає **рівно один рядок**,
`servpost.php` іноді віддає його як звичайний JSON-об'єкт, а не масив
з одним елементом (хоча зазвичай відповідь — масив об'єктів).
Задокументована рекомендація: якщо відповідь не є масивом —
обгортати в масив (`[дані]`), якщо `null`/порожньо — повертати `[]`.

> 🚨 **Розбіжність із фактичним кодом, поки не закрита.** Реальний
> парсер в обох бекенд-модулях (`payment.web.js`, `pricing.web.js`)
> робить **інакше** — не обгортає, а **відкидає** "голу" відповідь:
> ```js
> try {
>   const data = JSON.parse(raw);
>   return Array.isArray(data) ? data : [];   // ← НЕ [data], а []
> } catch (e) {
>   return [];
> }
> ```
> Тобто якщо `servpost.php` колись поверне рівно один рядок як "голий"
> об'єкт, цей рядок **мовчки губиться**, а не потрапляє в результат.
> Для запитів, де очікується рівно один рядок (наприклад,
> `getRequisites` у розділі 6.2 — конкретний ФОП), це потенційно
> небезпечно: код тихо піде у гілку "не знайдено"/фолбек, хоча рядок
> насправді був, просто в іншому форматі відповіді.
>
> Не факт, що це реальна проблема "в бою" — можливо, для конкретно цих
> SQL `servpost.php` завжди віддає масив, і "голий об'єкт" трапляється
> лише в інших сценаріях. Але **для Flask-версії** правильно —
> перевіряти обидва варіанти відповіді явно (масив і одиночний
> об'єкт) при парсингу, а не покладатись мовчки на жодну з двох
> поведінок, і логувати випадок "відповідь не масив", щоб побачити,
> чи таке взагалі трапляється. Варто також уточнити в розробника
> `servpost.php`, чи справді формат відповіді залежить від кількості
> рядків.

## 1. Розклад групових тренувань (`rasp`)

Використовується сторінкою **Розклад** (`docs/pages/08-schedule`).

Запит — на один конкретний день. Щоб отримати розклад на тиждень,
потрібно циклом пройтись по всіх днях тижня (`dn` від 1 до 7),
підставляючи потрібну дату.

Є два варіанти запиту:
- **Базовий** — просто розклад дня
- **Розширений** (з робочого Flutter-застосунку) — додатково враховує
  факт і кількість запису конкретного клієнта на тренування (через
  `zmain`/`zdop`). На сайті немає авторизованого клієнта як у
  застосунку — ймовірно, достатньо базового варіанту (уточнити)

### 1.1. Уточнення з реального Wix-коду сторінки Розклад

> Джерело: робочий (хоч і не фінальний) Velo-код сторінки Розклад —
> код сторінки, HTML-віджет сітки, бекенд-метод `getWeekSchedule`,
> джоба оновлення кешу.

**🚨 Критично: запити по днях тижня йдуть ПОСЛІДОВНО, не паралельно.**
У бекенді дні тижня опитуються один за одним із паузою **350 мс** між
запитами, а не через `Promise.all`. Причина прямо вказана в коментарі
розробника: раніше при паралельних запитах API повертав **504
Timeout**. **Обов'язково повторити цей підхід у нашому Flask-бекенді**
— зовнішній API не розрахований на навантаження паралельними
запитами.

**Кешування підтверджено так, як і планували:**
- `current` — поточний тиждень, оновлюється **щогодини** (cron `20 * * * *`)
- `next` — наступний тиждень, оновлюється **раз на 2 години** (менш критично)
- Кеш — по одному рядку на тиждень (`_id: "current"` / `"next"`),
  усі 7 днів серіалізовані в один JSON-блок (`weekData`), плюс
  `updatedAt` і `mondayDate`
- Тижні за межами `current`/`next` — читаються **наживо** з API при
  кожному запиті сторінки (weekOffset ≥ 2)

**Стійкість до помилок API:** якщо під час оновлення кешу день не
вдалося завантажити (помилка API для конкретного дня) — кеш **не
затирається порожніми даними**, залишаються попередні (старі) дані
для цього дня. Кожен день кешу оновлюється/зберігається незалежно від
інших — часткова помилка не валить весь тиждень.

**Інші деталі з UI:**
- Тренер показується на картці **лише ім'я + прізвище** (`i` + `f`),
  без по батькові (`o`), хоч API його й віддає
- `onlyad` реально використовується — картка занять "лише через
  адміна" виділяється окремим стилем із написом "Запис через адміна"
- У картках закладена логіка "місць немає" (`noSeats`), **але зараз
  завжди `false`** — реальний підрахунок вільних місць не
  реалізований (потребував би розширеного запиту з `zmain`/`kd`/`kr`,
  а ми домовились використовувати базовий запит). Залишаємо як
  можливе покращення на майбутнє, не для першої версії
- **Фільтри "Тренер" і "Вид тренування" взаємовиключні** — вибір
  одного скидає інший назад у "Всі". Варто врахувати в описі сторінки
  `08-schedule` (там зараз написано просто "2 випадні списки", без
  цього нюансу)
- Значення для випадних списків фільтрів **не окремий запит** — вони
  збираються з унікальних тренерів/типів тренувань, які вже є в
  завантаженому тижні
- **"Перестрибування" на найближчий тиждень:** якщо після вибору
  фільтра в кешованих 2 тижнях немає жодного заняття — сайт у фоні
  шукає найближчий тиждень із заняттями (по одному, наживо, до 12
  тижнів вперед) і сам перемикає перегляд туди. Приємна фіча, але не
  критична для MVP — можна відкласти на пізніше

## 3. Абонементи (`spab` + `abcen`)

Використовується для **списку тарифів на сторінці Прайс**.

| Поле | Опис |
|---|---|
| idgr | ІД групи (звʼязок з `grab`) |
| idch | ІД ФОП для оплати |
| vis | 0 — видалено, 1 — діюче |
| name | назва в обліковій програмі (внутрішня, історична) |
| nameapp | назва українською для застосунку/сайту; якщо не заповнено — використовувати `name` |
| kt | кількість тренувань: NULL — безліміт, інакше — ліміт |
| srd | термін дії абонемента, в днях |
| davt | днів до автоматичної активації |
| prapp | чи можна оплатити онлайн (кнопка "Оплатити") — якщо ні, показується "Оплата через адміністратора" |
| cym | ціна на обрану дату |
| namegrup | назва групи (опційно, через join на `grab`) |
| **prsite** | **показ на сайті** — булеве значення |

> 🔑 Поле **`prsite`** — саме той прапорець, за яким потрібно
> фільтрувати абонементи для показу на сторінці Прайс.
>
> ⚠️ **Виправлення:** у первинному PDF-довіднику це поле було записано
> як `prsait` — це помилка транскрипції. У реальному робочому Wix-коді
> скрізь послідовно використовується **`prsite`**. Довіряємо
> робочому коду, підтверджено фінальною версією `pricing.web.js`.
>
> Поле **`nameapp`** — не повне рішення проблеми "неправильних назв з
> API": воно буває і заповнене, але з некоректною назвою, не тільки
> порожнє. Тому власник повністю підміняє назву своєю Wix-таблицею
> (`PriceNamesConfig`, розділ 5.4), а не лише добудовує там, де
> `nameapp` порожній.

**Точна логіка визначення `cym` (ціни "на обрану дату"), підтверджена
фінальним кодом `getCards` у `pricing.web.js`:**

```sql
SELECT spab.id, spab.idch, spab.name, spab.nameapp, spab.srd, spab.prapp, c.cym
FROM spab
LEFT JOIN abcen c
  ON (c.ida = spab.id AND c.idz = 1)
  AND c.dv = (
    SELECT MAX(c2.dv) FROM abcen c2
    WHERE c2.ida = spab.id AND c2.dv <= '<сьогодні, dd.mm.yyyy>' AND c2.idz = 1
  )
WHERE spab.idz=1 AND spab.vis=1 AND spab.prsite='true' AND spab.idgr IN (...)
ORDER BY spab.name
```

Тобто `abcen` — це історія зміни ціни в часі (по одному рядку на дату
початку дії ціни), а не поточна ціна одним числом. Ціна `cym` —
рядок `abcen` з **найпізнішою датою `dv`, яка не пізніша за
сьогодні**. Важливо повторити цю логіку в Flask/PostgreSQL один в один
(корельований підзапит або віконна функція `ROW_NUMBER() OVER (...
ORDER BY dv DESC)` з фільтром `dv <= сьогодні`).

## Як це лягає на наші сторінки

- **Розклад** (`08-schedule`) → запит 1 (`rasp`), циклом по днях тижня
- **Прайс** (`09-price`) → запити 2+3 разом:
  - перший фільтр (категорії) = `grab` (де `shina = true`)
  - список тарифів у категорії = `spab`+`abcen`, відфільтровані по
    `idgr` і показані лише де `prsite = true`
  - другий (залежний) фільтр — не окреме поле в API, а власні
    Wix-таблиці власника (`PriceGroupsConfig.filterMode`, розділ 5)
  - запит 4 (`abu`) — деталізація складу абонемента, потрібна лише
    якщо на сайті буде розгортання "що входить"

## Рішення

- **Розклад:** використовуємо **базовий запит** (без урахування
  клієнта) — на сайті немає авторизованого відвідувача, як у
  застосунку
- **Кешування розкладу:** зберігаємо (кешуємо) у власній PostgreSQL
  **поточний і наступний тиждень** (2 тижні наперед). Якщо користувач
  клікає далі (тижні за межами цього вікна) — читаємо напряму з API
  "наживо", без кешування

## 5. Мапінг-таблиці для Прайсу (з Wix CMS)

Це чотири таблиці, які власник веде вручну в Wix — саме вони
"довизначають" те, чого не вистачає у сирих даних `grab`/`spab` з
API (правильні назви, розбивка на другий фільтр, текст умов, порядок
показу). При переїзді ці таблиці стають звичайними таблицями в нашій
PostgreSQL.

### 5.1. `PriceGroupsConfig` — перший рівень фільтра (категорії)

Мапить `grab.id` (з API) на категорію, яку бачить відвідувач сайту.
У коді сторінки Wix-колекція називається `Import2`.

| Поле | Опис |

| ID (slug) | внутрішній код категорії (`gym-no-trainer`, `massage`, `sauna`…) |
| sourceIdgrs | `grab.id` з API — масив (навіть якщо одне число) |
| displayName | назва категорії на сайті |
| order | порядок показу вкладки |
| filterMode | тип другого фільтра для цієї категорії: `srd` / `category` / `none` |

| personal | [12, 17] | Персональні тренування | 5 | category |
| massage | 5 | Масаж | 6 | category |
| sauna | 273 | Сауна | 7 | none |
| solarium | 254 | Солярій | 8 | none |

**`filterMode` визначає, звідки береться другий фільтр:**
- **`srd`** — другий фільтр = термін дії абонемента, береться напряму
  з поля `srd` в API (30 / 90 / 365 днів). Окрема таблиця не потрібна
- **`category`** — другий фільтр — довільна категорія (стать,
  кваліфікація тощо), яку API не знає. Потрібна `PricePlansConfig`
  (див. нижче)
- **`none`** — другого фільтра немає, показуємо всі тарифи групи одразу

> ✅ `gym-fitness` і `kids` навмисно дублюють одну й ту саму групу
> `390` — це не розбивка за вмістом, а один і той самий набір тарифів,
> який просто показується під двома різними вкладками категорій.
> Спеціальної логіки розрізнення абонементів не потрібно.

### 5.2. `PriceRulesConfig` — текст нижньої інформаційної плашки

У коді сторінки — колекція `Import4`. Ключ рядка (`_id`):
- для категорій з `filterMode = srd` → `${sourceIdgrs[0]}_${filterValue}` (наприклад `"2_30"`)
- для категорій з `filterMode = category` або `none` → `${tabSlug}_default` (наприклад `"massage_default"`, `"personal_default"`)

| Поле | Опис |
|---|---|
| _id | ключ, зібраний за правилом вище |
| rules | HTML-розмітка тексту плашки |

Ключовий висновок: для категорій `category`/`none` (масаж, персональні,
сауна, солярій) **текст плашки один і той самий незалежно від
обраного другого фільтра** — є лише один рядок `..._default`. Для
`srd`-категорій текст **різний для кожного терміну** (окремий рядок
на 30/90/365 днів).

Поточні записи: `2_30`, `2_90`, `2_365` (зал без тренера),
`287_30` (авторські — тільки 30 днів), `390_30`, `390_90` (зал+фітнес
/ діти), `massage_default`, `personal_default`, `sauna_default`,
`solarium_default`.

### 5.3. `PricePlansConfig` — призначення абонемента до другого фільтра (тільки для `category`-режиму)

У коді сторінки — колекція `Import3`. Використовується лише для
`massage` і `personal` — по одному рядку на кожен конкретний
абонемент (`_id` = `spab.id` з API).

| Поле | Опис |
|---|---|
| _id | `spab.id` конкретного абонемента з API |
| filterValue | значення другого фільтра для цього абонемента (`Жіночий` / `Чоловічий` / `Дитячий` для масажу; `CLASSIC` / `PRO` / `PRO+` / `VIP` / `VIP+` / `Авторський` для персональних) |
| order | порядок показу **вкладки** другого фільтра (групує рядки з однаковим `filterValue`, значення однакове для всіх рядків однієї групи) |
| displayName | поле існує в схемі, **але в поточному фінальному коді не використовується** для показу назви картки (див. 7.5) — не плутати з `order`, який реально впливає на порядок вкладок фільтра |

Приклад логіки: у масажу другий фільтр — стать/вік (`Жіночий`=1,
`Чоловічий`=2, `Дитячий`=3); у персональних — рівень тренера
(`CLASSIC`=1 … `Авторський`=6).

### 5.4. `PriceNamesConfig` — override назв абонементів **і порядку карток**

У коді сторінки — колекція `getNameOverrides`. Невелика таблиця (зараз
4 записи), яка замінює `nameapp` там, де назва з API все одно
неправильна/незрозуміла.

| Поле | Опис |
|---|---|
| _id | `spab.id` абонемента (для точного зіставлення) |
| displayName | назва, яку показуємо на сайті замість `nameapp` |
| order | **порядок показу конкретної картки** всередині обраного (другого) фільтра. Картки без заповненого `order` тут йдуть у кінець списку, а не на початок |

> 🔑 **Уточнено фінальним кодом:** `order` для сортування **карток
> усередині** обраного фільтра береться саме з цієї таблиці
> (`PriceNamesConfig`/`getNameOverrides`), а **не** з `order` у
> `PricePlansConfig`/`Import3` (той відповідає лише за порядок самих
> вкладок другого фільтра — "Жіночий"/"Чоловічий"/"Дитячий" як групи,
> однаковий для всіх карток групи, для сортування карток усередині
> групи не годиться).
>
> ✅ **Підтверджено фінальним кодом:** `PriceNamesConfig` (`displayName`
> **і** `order`) застосовується **для всіх категорій без винятку**,
> включно з масажем і персональними тренуваннями — не лише для решти
> категорій, як планувалось раніше. Поле `displayName` у
> `PricePlansConfig`/`Import3` (5.3) у коді для показу назви картки
> **не використовується** — це підтверджений факт фінального коду, а
> не недороблена частина (див. 7.5).

### Загальна логіка відображення сторінки Прайс

1. Перший фільтр (вкладки категорій) — з `PriceGroupsConfig`, в
   порядку `order`
2. Користувач обирає категорію → дивимось її `filterMode`:
   - `srd` → другий фільтр = унікальні `srd` (30/90/365) серед
     абонементів групи (з урахуванням правила 7.6 про `srd="1"`);
     текст плашки — з `PriceRulesConfig` за `sourceIdgrs[0]` + обраний `srd`
   - `category` → другий фільтр = унікальні `filterValue` з
     `PricePlansConfig` для абонементів групи, в порядку `order`;
     текст плашки — один `..._default` з `PriceRulesConfig`
   - `none` → другого фільтра немає; текст плашки — `..._default`
3. Список тарифів — абонементи (`spab`+`abcen`, розділ 3) з потрібним
   `idgr` і `prsite = true`, відфільтровані за обраним другим фільтром
4. Назва й порядок кожного тарифу — з `PriceNamesConfig`
   (`displayName`/`order`, розділ 5.4) для **будь-якої** категорії;
   якщо збігу за `_id` немає — назва бере `spab.nameapp` (або
   `spab.name`, якщо `nameapp` порожнє), картка йде в кінець списку

## 6. Оплата (LiqPay)

> Джерела: покроковий опис від розробника (документ по оплаті) +
> фінальний робочий код `payment.web.js` + HTML-віджет `#Content`
> (модалка оплати) + приклад реального коду запуску оплати з
> Flutter-застосунку.

Оплата іде через три скрипти: `servpost.php` — для пошуку клієнта й
перевірки реквізитів ФОПа (звичайні SQL-запити, як і раніше);
`genmanid.php` — окремий скрипт лише для резервування ID (`a`/`b`/`c`/`d`,
без SQL); і `liqpay_checkout.php` — сам редирект на оплату.

### 6.1. Ідентифікація клієнта за телефоном (з перевіркою чорного списку)

Без ідентифікації клієнта в базі продаж абонемента **не допускається**.
Важливий нюанс: **платник і покупець можуть бути різними людьми** —
хтось може купити абонемент будь-кому із зареєстрованих у залі, знаючи
його номер телефону. Тому після пошуку клієнта за телефоном обов'язково
**показати знайдене ПІБ і перепитати** "купуємо абонемент для цієї
людини?", перш ніж продовжити.

**Нормалізація номера (`payment.web.js`, `normalizePhone`):** приймає
будь-який формат (`0676325292`, `+380676325292`, `380676325292`...),
зводить до 10 цифр (провідний `380` замінює на `0`), форматує як
`"067 632-52-92"` для показу. Якщо після очистки не рівно 10 цифр —
одразу помилка `"Невірний формат номера телефону"`.

**Пошук у базі — порівняння лише цифр з обох боків** (детальніше в
7.2), без прив'язки до залу реєстрації клієнта (детальніше в 7.3):

```sql
select spk.idg, spk.f, spk.i, spk.o,
CASE
    WHEN a.id IS NOT NULL THEN 1
    ELSE 0
END AS bs
from spk
left join bsp a on (a.idkl = spk.idg and a.vis = 1)
where REPLACE(REPLACE(TRIM(spk.tel), ' ', ''), '-', '') = '<10 цифр номера>'
and spk.vis = 1
```

| Поле | Опис |
|---|---|
| idg | ІД клієнта. **Уточнення розробника:** сам по собі `idg` унікальний лише в межах одного залу — справжня унікальність рядка забезпечується парою `idz`+`idg` разом (див. 7.3) |
| f, i, o | прізвище, ім'я, по батькові клієнта |
| bs | **1 — клієнт у чорному списку, 0 — не в списку** |

> 🚨 **Критичне бізнес-правило.** Якщо `bs = 1` — продавати абонемент
> **не можна**. У нашому Flask-коді це має бути явна, добре покрита
> тестом перевірка — helper-функція типу `is_blacklisted(client) -> bool`,
> а не голе порівняння числа в шаблоні, щоб випадково не інвертувати
> логіку.

**🆕 На один номер телефону може бути зареєстровано декілька людей**
(підтверджено фінальним кодом і коментарем розробника — приклад:
мама і донька, обидві з ідентичним `tel`, але різними `idg`). SQL-запит
вище повертає **весь список**, не лише перший рядок:

```js
{ found: true, clients: [{ clientId, lastName, firstName, middleName, blacklisted }, ...], zalName }
```

Вибір, за кого саме оформляти оплату, робить людина за монітором —
модалка оплати (`#Content`) показує радіо-список ПІБ, якщо знайдено
більше одного клієнта.

> 🚨 **Бізнес-правило, яке варто підтвердити з власником.** Перевірка
> чорного списку в реальному коді робиться так:
> ```js
> const phoneIsBlacklisted = foundClients.some((c) => c.blacklisted);
> ```
> Тобто якщо на одному номері телефону зареєстровано кілька людей і
> **хоч одна** з них у чорному списку — оплата блокується для **всіх**
> людей на цьому номері, навіть якщо покупець хотів оформити абонемент
> саме на не-blacklisted людину. Незрозуміло, чи це свідоме рішення,
> чи побічний ефект логіки, написаної ще коли малось на увазі "один
> номер = одна людина". **Уточнити перед переписуванням:** чи повинна
> Flask-версія блокувати вибір конкретної (не blacklisted) людини зі
> списку, чи зберегти поточну поведінку "блокувати весь номер".

Якщо клієнта не знайдено в базі — показати номер телефону залу і
запропонувати спочатку зареєструватись, і лише після реєстрації
купувати абонемент. Без реєстрації продаж неможливий. (У фінальному
коді відповідь при "не знайдено" містить ще службове поле `debugPhone`
— нормалізований номер для налагодження; **не переносити в
Flask-версію**, це навмисно лишений debug-артефакт розробника, не
частина контракту API.)

> 🔒 **Приватність, варто врахувати при переписуванні.** Пошук клієнта
> за телефоном — публічний ендпоінт без авторизації: будь-хто, хто
> вгадає/переберe номер, отримає у відповідь ПІБ зареєстрованої людини
> і статус чорного списку. На нинішньому Wix-сайті це, можливо,
> прийнятний ризик (малий трафік, ендпоінт ніде публічно не
> рекламується), але для Flask-версії варто свідомо вирішити:
> рейт-лімітинг, капча чи інше обмеження на цей запит — щоб хтось не
> зміг масово "пробити" телефонну базу клубу через сайт.

### 6.2. Визначення ФОП (юрособи) для оплати

При виборі абонемента маємо `spab.idch` — ІД ФОПа, на який за
налаштуваннями має йти оплата. Але оплата на цей ФОП може бути не
налаштована, тому перевіряємо каскадом (підтверджено один в один
фінальним кодом `getRequisites`):

1. **Перевірка реквізитів для `spab.idch`:**
   `B`: `select * from spchpcon where idz='<ID залу>' and id=spab.idch and vis=1`
   Цікаві поля: **adro, opmerch, perky** — з них формується запит
   до LiqPay. Якщо хоч одне з трьох порожнє — переходимо до п. 2
   (реквізити за замовчуванням).
2. **Реквізити за замовчуванням для залу:**
   `B`: `select idchp from spzal where id='<ID залу>' and vis=1`
   Якщо `idchp` — `null` або `0` → оплати для залу взагалі не
   налаштовані, оплата недопустима.
3. **Повторюємо п. 1**, але з `id = IDCHP` (значення за замовчуванням
   з п. 2). Знову перевіряємо `adro`/`opmerch`/`perky` — якщо хоч одне
   порожнє, оплата не працює.

> Поля **`adro`/`opmerch`/`perky`** зберігаються в закодованому
> вигляді; як їх розшифровувати, знає лише сервер розробника. **Нам
> не потрібно їх декодувати самим** — просто зчитуємо ці три значення
> і передаємо далі як є в `liqpay_checkout.php` (сервер розкодує їх
> сам під час формування запиту до LiqPay).

### 6.3. Формування `ORDER_ID`, `unique_id` і резервування ID

`ORDER_ID` — складений рядок, потрібен нам самим, щоб точно
ідентифікувати, хто що купив і як оплатив. Формат сайту відрізняється
від застосунку **лише одним символом** (2-й символ):

```
Застосунок: 1B2Pl75428Op124449CH2a148Kl-99189921
Сайт:       1S2Pl75428Op124449CH2a148Kl-99189921
```

| Частина | Значення |
|---|---|
| `1` | номер мережі, у нас завжди 1 |
| `B` / `S` | джерело: `B` — застосунок, `S` — **сайт (наш випадок)** |
| `1` / `2` | ІД залу: 1 — FitZone (лівий берег), 2 — Ф3 |
| `Pl` | незмінний роздільник — перед ІД рядка продажу абонемента |
| `75428` | ІД рядка продажу абонемента (таблиця `prab`), резервується заново щоразу |
| `Op` | незмінний роздільник — перед ІД рядка оплати абонемента |
| `24449` | ІД рядка оплати (таблиця `fkb`), резервується заново щоразу |
| `CH` | незмінний роздільник — перед ІД ФОПа |
| `2` | ІД ФОПа (`spab.idch` або `IDCHP` за замовчуванням — з 6.2) |
| `a` | незмінний роздільник — перед ІД абонемента |
| `148` | ІД абонемента, що продається (`spab.id`) |
| `Kl` | незмінний роздільник — перед ІД клієнта |
| `-99189921` | ІД клієнта (**мінус на початку значущий**, в базі бувають від'ємні ІД) |

**Резервування ID (`prab` і `fkb`) перед формуванням `ORDER_ID`:**
окремий скрипт, не `servpost.php` — `genmanid.php`:
- `a`: `[1,1]` або `[1,2]`
- `b`: `["prab", "fkb"]` — масив таблиць, для яких потрібні нові ID
- `c`: ІД клієнта, який запитує ID
- `d`: `[1,1]` — кількість ID для кожної з таблиць (тут по 1)

Відповідь — JSON-масив вигляду `{table, new_id}`. З нього беремо:
`prab` → значення після `Pl`, `fkb` → значення після `Op`.

Результат: `1S<ІД_залу>Pl<prab>Op<fkb>CH<idch>a<spab.id>Kl<ІД_клієнта>`

**🆕 Формула `unique_id`, підтверджена фінальним кодом:**
```js
const uniqueId = `${orderId}_${Date.now()}`;
```
тобто `unique_id` = `order_id` + `_` + Unix-timestamp у мілісекундах
на момент формування (не окремий лічильник і не UUID).

**🆕 Формат `description`,** як реально збирається в модалці оплати
(`#Content`) перед відправкою на бекенд:
```
"<Прізвище Ім'я По-батькові> — <назва абонемента, spab.nameapp/name> — Оплата через сайт"
```
Назва абонемента тут — **оригінальна** `nameapp`/`name`, без
override з `PriceNamesConfig` (5.4): у підтвердженні оплати показується
"сира" назва з API, а не "красива" назва, яка показана на картці в
прайсі. Варто звірити весь UI на цю різницю показна-назва-в-картці vs
назва-в-підтвердженні-оплати при переписуванні — можливо, це варто
уніфікувати.

Коли адміністратор потім обробляє рядок оплати — в нього вже є
зв'язок клієнт → абонемент → ФОП → зарезервований звʼязок
абонемент-оплата.

### 6.4. Запуск `liqpay_checkout.php`

Приклад виклику (Flutter-застосунок, для довідки — на сайті та сама
логіка, підтверджено фінальним кодом `prepareCheckout`, тільки без
Flutter-специфіки):

```dart
final checkoutPage = 'https://app.fitzone.com.ua/zdeccidatmoiscripti/liqpay_checkout.php';
final uri = Uri.parse(checkoutPage).replace(queryParameters: {
  'A': jsonEncode([network.id, gym.id]),
  'amount': amount.toStringAsFixed(2),
  'order_id': orderId,
  'unique_id': uniqueId,
  'timestamp': timestamp.toString(),
  'description': description,
  'adro': paymentAdro,
  'opmerch': paymentOpmerch,
  'perky': paymentPerky,
});
```

Скрипт сам формує все необхідне для LiqPay і редиректить на сторінку
оплати. Сайт робить повний редирект вікна (`window.top.location.href
= checkoutUrl`), без своєї проміжної сторінки очікування.

> **Відмінність сайту від застосунку:** у Flutter-коді є купа
> Safari-специфічної логіки (`SafariHelper`, "anti-cache" параметри,
> запуск як зовнішній застосунок, опитування статусу одразу після
> запуску) — це обхідні шляхи для проблем iOS WebView/Safari
> усередині мобільного застосунку. **На сайті цього не потрібно** —
> досить звичайного редиректу браузера (`window.location.href` /
> `redirect()` на Flask-стороні) на сформований `checkoutPage`-URL.

### 6.5. Що відбувається після оплати

Клієнт обирає спосіб оплати на сторінці LiqPay і платить. Банк сам
шле колбек на сервер застосунку — скрипт автоматично приймає колбек
і записує оплату в таблицю. Персонал клубу отримує сповіщення від
банку, підтверджує двома кнопками — абонемент вважається проданим.

**Це відбувається повністю на боці сервера розробника — від нашого
Flask-бекенду тут більше нічого не залежить.**

Розробник радить **не** робити на сайті повноцінне опитування статусу
оплати й автоматичну активацію — це вимагає багато додаткових
запитів. Достатньо показати клієнту повідомлення на кшталт: *"Якщо ви
провели оплату — ми обов'язково отримаємо підтвердження від банку і
здійснимо продаж обраного вами абонемента"* (так само зроблено в
застосунку).

## 7. Уточнення з робочого (фінального) Wix-коду

> Джерело: фінальний робочий Velo-код сторінки Прайс (`payment.web.js`,
> `pricing.web.js`, три HTML-віджети — `#Filters`, `#Content`,
> `#Rules` — і код сторінки).

### 7.1. Виправлення: поле називається `prsite`, не `prsait`

У всіх SQL-запитах реального коду послідовно використовується
`spab.prsite = 'true'`. У PDF-довіднику це поле записано як `prsait`
— найімовірніше, помилка транскрипції розробника. Виправлено по
всьому документу вище.

### 7.2. Пошук клієнта за телефоном — надійніший підхід, ніж очікувалось

PDF наполягав, що телефон зберігається рівно у форматі
`" 067 632-52-92"` (з пробілом на початку) і шукати треба точним
збігом. Реальний код цю крихкість обходить: **нормалізує обидві
сторони порівняння**, прибираючи пробіли й тире і зіставляючи лише
цифри (SQL — див. 6.1). Додатково `normalizePhone` на вході приймає й
формат із кодом країни без `+` (`380...`) — замінює провідний `380`
на `0` перед подальшою обробкою.

**Рекомендація для нашого Flask-бекенду:** робити так само — зберігати
й порівнювати телефони як "тільки цифри", а не покладатись на точний
формат із пробілами й тире. Значно надійніше.

Також у коді є розгорнута debug-логіка (пошук по останніх 7 цифрах
через `LIKE`, виведення сирого значення `spk.tel` з бази) — це
залишено розробником навмисно для налагодження формату, а не постійна
частина функціоналу. У фінальній версії такого не буде.

### 7.3. Реєстрація клієнта в іншому залі — не перешкода

Власник напряму уточнив питання в розробника, відповідь чітка:

> "Пофіг, куди він зареєстрований. Не повинно бути прив'язки до
> реєстрації клієнта в якому-небудь залі мережі — пофіг. Повинна бути
> прив'язка, в який зал купуєш, інакше буде каша з ID при продажу.
> Тільки у клієнта унікальний `idg` у кожному залі, унікальність рядка
> забезпечується поєднанням `idz`+`id`."

Тобто:
- **До якого залу "приписаний" клієнт — не має значення.** Клієнта з
  будь-яким номером телефону можна знайти й продати йому абонемент
  FitZone, навіть якщо він "числиться" в Ф3
- **Важливо тільки, в який зал відбувається сама покупка** — саме
  `idz` (зал) транзакції визначає, під яким `idz`+`idg` шукати/писати
  клієнта, а не якась перевірка "приналежності"
- **`idg` сам по собі не унікальний мережево** — унікальний лише
  рядок `idz`+`idg` разом

**Вимога до UI (підтверджена фінальним кодом):** перед натисканням
"Оплатити" сайт явно показує і просить підтвердити, **для якого залу**
купується абонемент (модалка `#Content`, крок підтвердження — рядок
`"ЗАЛ: FitZone"`), і що це саме той клієнт — за ПІБ, з кнопками
"скасувати"/"продовжити".

### 7.4. Уточнення поля `prapp`

У PDF-довіднику `prapp` описано просто як "показ у мобільному
застосунку". У реальному коді це поле визначає, чи можна **оплатити
абонемент онлайн прямо на сторінці**:
- `prapp = true` → показується кнопка "Оплатити" (веде на LiqPay)
- `prapp = false/null` → показується плашка "Оплата через
  адміністратора" замість кнопки

### 7.5. Override назви й порядку карток — підтверджено: єдина таблиця для всіх категорій

Раніше (за черновим Wix-кодом) припускалось, що для масажу й
персональних override імені йде через `PricePlansConfig`, а для решти
категорій — через `PriceNamesConfig`. **Фінальний код підтверджує, що
насправді так не є, і це не недоробка, а стабільна поведінка:**
override завжди береться з однієї таблиці (`getNameOverrides` =
`PriceNamesConfig`, розділ 5.4) для будь-якої категорії, включно з
масажем/персональними.

Уточнено додатково (не було видно в черновому коді): та сама таблиця
`PriceNamesConfig` віддає ще й `order` — **порядок конкретної картки**
всередині обраного другого фільтра. Поле `order` у `PricePlansConfig`
(5.3) — це інший `order`, він відповідає лише за порядок **самих
вкладок** другого фільтра ("Жіночий"/"Чоловічий"/"Дитячий" як групи),
не за порядок карток усередині вибраної вкладки. Деталі й повна логіка
сортування — розділ 5.4.

### 7.6. Особливість: разові абонементи (`srd = "1"`) навмисно показуються під фільтром "30 днів"

Знайдено правило в коді:

```js
const SRD_ONE_AS_THIRTY = [2, 287]; // gym-no-trainer, authors
```

Для груп із `sourceIdgrs` 2 (Тренажерний зал без тренера) і 287
(Авторські абонементи) значення `srd = "1"` трактується як `"30"`
(днів) — і при формуванні списку значень другого фільтра, і при
фільтрації карток за обраним терміном.

**Це не помилка в даних, а навмисне рішення власника:** разові
("одноразові") абонементи навмисно показуються під вкладкою
"30 днів", щоб не створювати окрему рідковживану вкладку "1 день" у
фільтрі. За потреби можна додати окремий фільтр "1 день" — власник
відкрита до цього, якщо стане критично важливо.

### 7.7. Формат тіла запиту: реальні ключі — малими літерами

Див. розділ "Параметри запиту" вгорі документа — вже інтегровано.

### 7.8. Відповідність Wix-колекцій нашим CSV-таблицям

Робочий код звертається до колекцій із загальними назвами (схоже на
автогенеровані імена після імпорту CSV в Wix, які просто не
перейменували):

| Wix-колекція в коді | Відповідає |
|---|---|
| `Import2` | `PriceGroupsConfig` (перший фільтр/категорії) |
| `Import3` | `PricePlansConfig` (призначення абонемента до другого фільтра) |
| `Import4` | `PriceRulesConfig` (текст нижньої плашки) |
| `getNameOverrides` | `PriceNamesConfig` (override назв і порядку) |

В `Import2` поле масиву джерел називається `sourceIdgrs` (з "s" в
кінці), а не `sourceIdgr`, як у CSV — дрібниця, але важлива при звірці
полів.

### 7.9. Архітектура сторінки Прайс: три віджети, не два

Сторінка на Wix зроблена як **три** HTML-віджети (кастомні
iframe-компоненти), не два, кожен зі своїм `postMessage`-протоколом.
Диспетчер — код сторінки (Velo page code); більше ніде логіки немає.

| Елемент Wix | Відповідає за |
|---|---|
| `#Filters` | Перший рівень (категорії) + другий рівень (термін/стать/рівень) фільтрів. Сам нічого не запитує — лише малює те, що йому передали, і шле назад вибір користувача |
| `#Content` | Список тарифів, текст правил унизу, **уся модалка оплати** (кроки — телефон → вибір людини → підтвердження → чорний список → редирект) |
| `#Rules` | Статичний текст умов оплати + посилання на FitControl (Google Play / App Store). На десктопі показує блок одразу; на мобільному — згорнута кнопка |

**Протокол повідомлень:**

`#Filters` → сторінка: `ready` → `{initTabs}`/`{setFilters}` у відповідь;
`tabSelected {tabId}`; `filterSelected {filterValue}`.

`#Content` → сторінка: `ready`; `scrollToTop` (перед відкриттям
будь-якої модалки); `findClient {phone}`; `confirmClient {clientId,
planId, idch, price, description}`.
Сторінка → `#Content`: `loading`; `render {cards, rules}`;
`clientResult {result}`; `checkoutError {message}`; `openCheckout
{url}` (віджет робить `window.top.location.href = url`);
`showRulesModal` (реле від `#Rules`, див. нижче).

`#Rules` → сторінка: `ready`; `openPaymentRules` (клік по згорнутій
кнопці — лише мобільна версія; на десктопі текст видно одразу).

**🆕 Реле-механізм плашки правил.** Модалка з текстом правил фізично
намальована **всередині HTML `#Content`**, а не в `#Rules` — `#Rules`
лише плашка/кнопка. На мобільному клік по кнопці в `#Rules` шле
`openPaymentRules` у код сторінки, той релеїть це як `showRulesModal`
у `#Content`, і той відкриває свою вбудовану модалку:

```js
$w('#Rules').onMessage((event) => {
  if (event.data?.type === 'openPaymentRules') {
    $w('#Content').postMessage({ type: 'showRulesModal' });
  }
});
```

**Для Flask-переписування:** увесь цей реле-механізм — суто обхідний
шлях під обмеження Wix (iframe-и не бачать одне одного напряму). У
Flask це один DOM без iframe-ізоляції, тому кнопка правил просто
напряму відкриває той самий `<div class="modal-overlay">` — окремого
"реле" не буде взагалі. Важливо зберегти лише сам UX-факт: клік по
плашці правил на мобільному відкриває **ту саму** модалку, що й
кнопка "Оплатити" (просто одразу на кроці з текстом правил, а не
кроці телефону).

**UX-флоу модалки оплати (кроки, повністю):**

1. **Телефон** — інпут + кнопка "Знайти клієнта"
2. **Завантаження** — поки йде `findClient`
3. Результат:
   - помилка/не знайдено → назад на крок 1 з повідомленням
   - чорний список (правило "хоч один із знайдених", 6.1) → **"Оплата
     недоступна"**, тільки кнопка "Закрити"
   - 1 людина знайдена → одразу крок 4
   - кілька людей → радіо-список ПІБ, "Продовжити"/"Назад"
4. **Підтвердження** — ПІБ, `"ЗАЛ: FitZone"`, назва абонемента (сира
   `nameapp`, не override), сума. "Так, оформити на цю людину" /
   "Відхилити / Назад"
5. **Завантаження** → `confirmClient` → бекенд формує `checkoutUrl`
6. Успіх → повний редирект браузера на LiqPay
7. Помилка формування оплати → назад на крок 1 з текстом помилки

**Кешування на рівні сторінки (Velo page code), не БД:** JS-змінні,
які живуть, поки відкрита вкладка браузера, зникають при
перезавантаженні сторінки — `filtersCache[tabId]`,
`cardsCache["${tabId}::${filterValue}"]`. Плюс `pendingRender` —
буфер на випадок, якщо повідомлення для `#Content` треба надіслати
до того, як віджет встиг прислати своє `ready` (гонка при першому
завантаженні). **Для Flask-версії:** це суто client-side UX-поведінка
(уникнути повторних AJAX-запитів при перемиканні між уже відвіданими
табами/фільтрами в межах однієї сесії) — варто повторити на рівні
фронтенд-JS (простий об'єкт/`Map` у пам'яті сторінки), а не переносити
як серверне кешування.

### 7.10. Внутрішні/debug-ендпоінти, не частина продакшн-флоу

`pricing.web.js` містить `getAllRawNames()` — одноразовий аудит-скрипт
(сирі `name`/`nameapp` по всіх групах, коментар у коді: "запускати
синьою стрілкою в редакторі, без сторінки") і `ping()` — health-check.
**Для Flask-переписування не потрібні** як окремі публічні ендпоінти —
хіба що власник захоче аналогічний адмін-інструмент для аудиту назв,
тоді це окрема розмова, не частина публічного API сторінки Прайс.
