Зовнішнє API: servpost.php
Довідник побудований на основі PDF від розробника застосунку ("Fitzone / F3 — справочник по servpost.php"). Це єдине зовнішнє джерело даних для розкладу та прайсу — окремого API для прайсу немає.
Загальна інформація
ПараметрЗначенняСерверhttps://app.fitzone.com.uaШлях скрипта/zdeccidatmoiscripti/servpost.phpМетодPOSTФормат відповідічистий JSON (порожній JSON, якщо даних немає)Параметри запиту
• A — масив, визначає клуб: [1,1] — FitZone, [1,2] — Ф3
• B — рядок із SQL-запитом; конкретний запит відрізняється для кожної задачі (див. розділи нижче)
⚠️ Технічна примітка. Параметр B приймає "сирий" SQL-текст. У нашому Flask-бекенді маємо використовувати лише фіксовані, заздалегідь підготовлені запити (як задокументовано нижче) і ніколи не підставляти туди довільний користувацький ввід — щоб не відкрити SQL-injection через проксі-виклик цього API.
Про клуби (мультитенантність)
Цей API обслуговує одразу два клуби на одному сервері: FitZone (idz=1) і Ф3 (idz=2). У всіх SQL-запитах idz у тілі запиту має відповідати параметру A. Для нашого сайту цікавий лише idz=1 (FitZone).
Boolean-поля
Значення можуть приходити в різному вигляді:
• false ⇔ Null, f, false, 0
• true ⇔ t, true, 1
Формат непостійний — на боці Flask потрібна власна нормалізуюча функція при парсингу відповіді.

1. Розклад групових тренувань (rasp)
Використовується сторінкою Розклад (docs/pages/08-schedule).
Запит — на один конкретний день. Щоб отримати розклад на тиждень, потрібно циклом пройтись по всіх днях тижня (dn від 1 до 7), підставляючи потрібну дату.
Є два варіанти запиту:
• Базовий — просто розклад дня
• Розширений (з робочого Flutter-застосунку) — додатково враховує факт і кількість запису конкретного клієнта на тренування (через zmain/zdop). На сайті немає авторизованого клієнта як у застосунку — ймовірно, достатньо базового варіанту (уточнити)

2. Групи абонементів (grab)
Використовується як перший рівень фільтра на сторінці Прайс (категорії на кшталт "Тренажерний зал", "Масаж" тощо).
ПолеОписidІД групиnameназва групиshinaпоказ у мобільному застосунку: true — показувати, null/false — ніvis0 — видалена, 1 — діючаНа українській мові виводяться лише групи, у яких shina = true. За потреби решту назв можна перекласти.

3. Абонементи (spab + abcen)
Використовується для списку тарифів на сторінці Прайс.
ПолеОписidgrІД групи (звʼязок з grab)idchІД ФОП для оплатиvis0 — видалено, 1 — діючеnameназва в обліковій програмі (внутрішня, історична)nameappназва українською для застосунку/сайту; якщо не заповнено — використовувати namektкількість тренувань: NULL — безліміт, інакше — лімітsrdтермін дії абонемента, в дняхdavtднів до автоматичної активаціїprappпоказ у мобільному застосункуcymціна на обрану датуnamegrupназва групи (опційно, через join на grab)prsaitпоказ на сайті — булеве значення🔑 Поле prsait — саме той прапорець, за яким потрібно фільтрувати абонементи для показу на сторінці Прайс.
Поле nameapp — не повне рішення проблеми "неправильних назв з API": воно буває і заповнене, але з некоректною назвою, не тільки порожнє. Тому власник повністю підміняє назву своєю Wix-таблицею (третя з трьох таблиць), а не лише добудовує там, де nameapp порожній. Очікуємо цю таблицю + опис того, як вона влаштована.

4. Послуги абонемента (abu + spu + abcenu)
Деталізація, що входить у конкретний абонемент.
ПолеОписidaІД абонементаiduІД послугиvis0 — видалено, 1 — дієkoluкількість послуг: 1000 — безліміт, -1 — визначається абонементом, інакше — числоnameназва послугиcymціна послуги (потрібна лише при прямому формуванні проданого абонемента)
Як це лягає на наші сторінки
• Розклад (08-schedule) → запит 1 (rasp), циклом по днях тижня
• Прайс (09-price) → запити 2+3 разом: 
o перший фільтр (категорії) = grab (де shina = true)
o список тарифів у категорії = spab+abcen, відфільтровані по idgr і показані лише де prsait = true
o другий (залежний) фільтр — поки не видно в цьому API окремим полем; можливо, це і є одна з ваших трьох Wix-таблиць (фільтри для Масаж/Персональні) — звірити, коли пришлете
o запит 4 (abu) — деталізація складу абонемента, потрібна лише якщо на сайті буде розгортання "що входить"
Рішення
• Розклад: використовуємо базовий запит (без урахування клієнта) — на сайті немає авторизованого відвідувача, як у застосунку
• Кешування розкладу: зберігаємо (кешуємо) у власній PostgreSQL поточний і наступний тиждень (2 тижні наперед). Якщо користувач клікає далі (тижні за межами цього вікна) — читаємо напряму з API "наживо", без кешування
5. Мапінг-таблиці для Прайсу (з Wix CMS)
Це чотири таблиці, які власник веде вручну в Wix — саме вони "довизначають" те, чого не вистачає у сирих даних grab/spab з API (правильні назви, розбивка на другий фільтр, текст умов). При переїзді ці таблиці стають звичайними таблицями в нашій PostgreSQL.
5.1. PriceGroupsConfig — перший рівень фільтра (категорії)
Мапить grab.id (з API) на категорію, яку бачить відвідувач сайту.
ПолеОписID (slug)внутрішній код категорії (gym-no-trainer, massage, sauna…)sourceIdgrgrab.id з API — може бути одне число або масив кількох iddisplayNameназва категорії на сайтіorderпорядок показу вкладкиfilterModeтип другого фільтра для цієї категорії: srd / category / noneПоточні 8 категорій:
slugsourceIdgrdisplayNameorderfilterModegym-no-trainer2Тренажерний зал без тренера1srdgym-fitness390Тренажерний зал +фітнес2srdkids390Дитячі абонементи3srdauthors287Авторські абонементи4srdpersonal[12, 17]Персональні тренування5categorymassage5Масаж6categorysauna273Сауна7nonesolarium254Солярій8nonefilterMode визначає, звідки береться другий фільтр:
• srd — другий фільтр = термін дії абонемента, береться напряму з поля srd в API (30 / 90 / 365 днів). Окрема таблиця не потрібна
• category — другий фільтр — довільна категорія (стать, кваліфікація тощо), яку API не знає. Потрібна PricePlansConfig (див. нижче)
• none — другого фільтра немає, показуємо всі тарифи групи одразу
✅ Уточнено: gym-fitness і kids навмисно дублюють одну й ту саму групу 390 — це не розбивка за вмістом, а один і той самий набір тарифів, який просто показується під двома різними вкладками категорій. Спеціальної логіки розрізнення абонементів не потрібно.
5.2. PriceRulesConfig — текст нижньої інформаційної плашки
Ключ — комбінація sourceIdgr + filterValue, значення — готовий HTML з умовами (термін, активація, заморозка, подовження тощо).
ПолеОписsourceIdgrgrab.id, до якого належить правилоfilterValueзначення другого фільтра: конкретне число днів ("30", "90", "365") для srd-категорій, або "default" для category/none-категорійrulesHTML-розмітка тексту плашкиКлючовий висновок: для категорій з filterMode = category або none (масаж, персональні, сауна, солярій) текст плашки один і той самий незалежно від обраного другого фільтра — є лише один рядок "..._default". Для srd-категорій текст різний для кожного терміну (окремий рядок на 30/90/365 днів).
Поточні записи: 2_30, 2_90, 2_365 (зал без тренера), 287_30 (авторські — тільки 30 днів), 390_30, 390_90 (зал+фітнес / діти), massage_default, personal_default (без sourceIdgr, бо в personal два джерела — 12 і 17), sauna_default, solarium_default.
5.3. PricePlansConfig — призначення абонемента до другого фільтра (тільки для category-режиму)
Використовується лише для massage і personal — по одному рядку на кожен конкретний абонемент (ID = spab.id з API).
ПолеОписIDspab.id конкретного абонемента з APIfilterValueзначення другого фільтра для цього абонемента (Жіночий / Чоловічий / Дитячий для масажу; CLASSIC / PRO / PRO+ / VIP / VIP+ / Авторський для персональних)orderпорядок показу вкладки другого фільтраdisplayNameнеобов'язковий override назви саме для цього абонемента (якщо пусто — береться назва з API/PriceNamesConfig)Приклад логіки: у масажу другий фільтр — стать/вік (Жіночий=1, Чоловічий=2, Дитячий=3); у персональних — рівень тренера (CLASSIC=1 … Авторський=6).
5.4. PriceNamesConfig — загальний override назв абонементів
Невелика таблиця-виняток (зараз 4 записи) для випадків, коли назва з API (nameapp) все одно неправильна/незрозуміла, і жодна з інших таблиць це не покриває.
ПолеОписoriginal nameappзначення nameapp з API, яке треба замінити_idspab.id абонемента (для точнішого зіставлення, не лише за текстом)displayNameназва, яку показуємо на сайті замість nameapp✅ Уточнено: PriceNamesConfig застосовується для решти категорій — зал (без тренера / +фітнес), діти, авторські, сауна, солярій. Для масажу й персональних тренувань override назви завжди йде через PricePlansConfig, PriceNamesConfig для них не використовується.
Загальна логіка відображення сторінки Прайс
1. Перший фільтр (вкладки категорій) — з PriceGroupsConfig, в порядку order
2. Користувач обирає категорію → дивимось її filterMode: 
o srd → другий фільтр = унікальні srd (30/90/365) серед абонементів групи; текст плашки — з PriceRulesConfig за sourceIdgr + обраний srd
o category → другий фільтр = унікальні filterValue з PricePlansConfig для абонементів групи, в порядку order; текст плашки — один ..._default з PriceRulesConfig
o none → другого фільтра немає; текст плашки — ..._default
3. Список тарифів — абонементи (spab+abcen) з потрібним idgr і prsait = true, відфільтровані за обраним другим фільтром
4. Назва кожного тарифу: 
o для масажу й персональних → PricePlansConfig.displayName (якщо заповнено), інакше spab.nameapp / spab.name
o для решти категорій (зал, діти, авторські, сауна, солярій) → PriceNamesConfig.displayName (якщо є збіг за _id), інакше spab.nameapp / spab.name
