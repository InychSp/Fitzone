# Зовнішнє API: servpost.php

> Довідник побудований на основі PDF від розробника застосунку
> ("Fitzone / F3 — справочник по servpost.php"). Це єдине зовнішнє
> джерело даних для розкладу та прайсу — окремого API для прайсу
> немає.

## Загальна інформація

| Параметр | Значення |
|---|---|
| Сервер | `https://app.fitzone.com.ua` |
| Шлях скрипта | `/zdeccidatmoiscripti/servpost.php` |
| Метод | POST |
| Формат відповіді | чистий JSON (порожній JSON, якщо даних немає) |

## Параметри запиту

- **A** — масив, визначає клуб: `[1,1]` — FitZone, `[1,2]` — Ф3
- **B** — рядок із SQL-запитом; конкретний запит відрізняється для
  кожної задачі (див. розділи нижче)

> ⚠️ **Технічна примітка.** Параметр `B` приймає "сирий" SQL-текст.
> У нашому Flask-бекенді маємо використовувати лише фіксовані,
> заздалегідь підготовлені запити (як задокументовано нижче) і
> ніколи не підставляти туди довільний користувацький ввід — щоб не
> відкрити SQL-injection через проксі-виклик цього API.

## Про клуби (мультитенантність)

Цей API обслуговує одразу два клуби на одному сервері: **FitZone**
(`idz=1`) і **Ф3** (`idz=2`). У всіх SQL-запитах `idz` у тілі запиту
має відповідати параметру `A`. **Для нашого сайту цікавий лише
`idz=1` (FitZone).**

## Boolean-поля

Значення можуть приходити в різному вигляді:
- false ⇔ `Null`, `f`, `false`, `0`
- true ⇔ `t`, `true`, `1`

Формат непостійний — на боці Flask потрібна власна нормалізуюча
функція при парсингу відповіді.

## 1. Розклад групових тренувань (`rasp`)

Використовується сторінкою **Розклад** (`docs/pages/08-schedule`).

Запит — на один конкретний день. Щоб отримати розклад на тиждень,
потрібно циклом пройтись по всіх днях тижня (`dn` від 1 до 7),
підставляючи потрібну дату.

Є два варіанти запиту:
- **Базовий** — просто розклад дня
- **Розширений** (з робочого Flutter-застосунку) — додатково враховує
  факт і кількість запису конкретного клієнта на тренування (через
  `zmain`/`zdop`). На сайті немає авторизованого клієнта як у
  застосунку — ймовірно, достатньо базового варіанту (уточнити)

### Поля відповіді

| Поле | Тип | Опис |
|---|---|---|
| idz | longint | ід залу (клубу) |
| id | longint | ід запису розкладу |
| idzal | longint | ід приміщення в залі |
| idtr | longint | ід тренера |
| vis | smallint | 0 — видалено, 1 — видиме |
| idu | longint | ід послуги |
| dn | smallint | день тижня: 1 — понеділок … 7 — неділя |
| vr | time | час початку тренування |
| vk | time | час закінчення тренування |
| ntr | varchar(30) | назва тренування |
| rabst | boolean | показ на робочому столі |
| ds | timestamp | дата початку тренувань |
| df | timestamp | дата останнього тренування; NULL — без обмеження |
| kd | smallint | допустима кількість місць для запису |
| kr | smallint | допустима кількість резервних місць |
| kzap | boolean | чи потрібно контролювати запис |
| shina | boolean | показувати в застосунку |
| zapkl / zapad / zaptr | smallint | за скільки днів максимум може записатись клієнт / адміністратор / тренер |
| otpis | smallint | за скільки годин до початку вже не можна відписатись |
| onlyad | boolean | запис можливий лише адміністратором/тренером |
| vid | varchar(40) | назва послуги |
| zal | varchar(25) | назва приміщення в залі |
| f, i, o | varchar | прізвище, ім'я, по батькові тренера |
| dot | timestamp | дата скасування; якщо збігається з датою запиту — тренування на сьогодні скасоване |

*(службові поля `ps, dps, dos, prus` — не потрібні; поля розширеного
запиту `vrtr, mntr, prmzap, kolzap, prdzap` — актуальні лише для
розширеного варіанту з обліком клієнта)*

## 2. Групи абонементів (`grab`)

Використовується як **перший рівень фільтра на сторінці Прайс**
(категорії на кшталт "Тренажерний зал", "Масаж" тощо).

| Поле | Опис |
|---|---|
| id | ІД групи |
| name | назва групи |
| shina | показ у мобільному застосунку: true — показувати, null/false — ні |
| vis | 0 — видалена, 1 — діюча |

> На українській мові виводяться лише групи, у яких `shina = true`.
> За потреби решту назв можна перекласти.

## 3. Абонементи (`spab` + `abcen`)

Використовується для **списку тарифів на сторінці Прайс**.

| Поле | Опис |
|---|---|
| idgr | ІД групи (звʼязок з `grab`) |
| idch | ІД ФОП для оплати |
| vis | 0 — видалено, 1 — діюче |
| name | назва в обліковій програмі (внутрішня, історична) |
| nameapp | назва українською для застосунку/сайту; якщо не заповнено — використовувати `name` |
| kt | кількість тренувань: NULL — безліміт, інакше — ліміт |
| srd | термін дії абонемента, в днях |
| davt | днів до автоматичної активації |
| prapp | показ у мобільному застосунку |
| cym | ціна на обрану дату |
| namegrup | назва групи (опційно, через join на `grab`) |
| **prsait** | **показ на сайті** — булеве значення |

> 🔑 Поле **`prsait`** — саме той прапорець, за яким потрібно
> фільтрувати абонементи для показу на сторінці Прайс.
>
> Поле **`nameapp`** — не повне рішення проблеми "неправильних назв з
> API": воно буває і заповнене, але з некоректною назвою, не тільки
> порожнє. Тому власник повністю підміняє назву своєю Wix-таблицею
> (третя з трьох таблиць), а не лише добудовує там, де `nameapp`
> порожній. Очікуємо цю таблицю + опис того, як вона влаштована.

## 4. Послуги абонемента (`abu` + `spu` + `abcenu`)

Деталізація, що входить у конкретний абонемент.

| Поле | Опис |
|---|---|
| ida | ІД абонемента |
| idu | ІД послуги |
| vis | 0 — видалено, 1 — діє |
| kolu | кількість послуг: 1000 — безліміт, -1 — визначається абонементом, інакше — число |
| name | назва послуги |
| cym | ціна послуги (потрібна лише при прямому формуванні проданого абонемента) |

## Як це лягає на наші сторінки

- **Розклад** (`08-schedule`) → запит 1 (`rasp`), циклом по днях тижня
- **Прайс** (`09-price`) → запити 2+3 разом:
  - перший фільтр (категорії) = `grab` (де `shina = true`)
  - список тарифів у категорії = `spab`+`abcen`, відфільтровані по
    `idgr` і показані лише де `prsait = true`
  - другий (залежний) фільтр — поки не видно в цьому API окремим
    полем; можливо, це і є одна з ваших трьох Wix-таблиць (фільтри
    для Масаж/Персональні) — звірити, коли пришлете
  - запит 4 (`abu`) — деталізація складу абонемента, потрібна лише
    якщо на сайті буде розгортання "що входить"

## Рішення

- **Розклад:** використовуємо **базовий запит** (без урахування
  клієнта) — на сайті немає авторизованого відвідувача, як у
  застосунку
- **Кешування розкладу:** зберігаємо (кешуємо) у власній PostgreSQL
  **поточний і наступний тиждень** (2 тижні наперед). Якщо користувач
  клікає далі (тижні за межами цього вікна) — читаємо напряму з API
  "наживо", без кешування
- Дві "перехідні" Wix-таблиці (фільтри Масаж/Персональні, текст
  нижньої плашки) аналогів у цьому API не мають — це суто UI-текст
  з боку Wix, окремо від даних API. Очікуємо самі таблиці
